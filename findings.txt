Redstone T2I — Experiment Log
==============================

Project Goal
------------
A transformer-based model that generates 28x28 binary images from text labels
(Quick Draw dataset, 345 categories), intended for eventual reimplementation
in Minecraft Redstone.

Architecture (baseline)
------------------------
- Decoder-only GPT-style transformer
- Vocab: 345 class words + 2 pixel tokens (0=white, 1=black) = 347 tokens
- Context length: 785 (1 word token + 784 pixel tokens)
- Embedding dim: 256, 8 heads, 6 layers, dropout 0.1
- ~10M parameters (256-dim), ~1.4M parameters (128-dim)
- Sequence format: [word_id, pixel_0, pixel_1, ..., pixel_783]
- Generation: top-k sampling with temperature


Training Data
-------------
Initial:  100,000 training images, 5,000 validation images (~290 per class)
Updated:  345,000 training images, 34,500 validation images (~1,000 per class)

Rationale: with only ~290 images per class, the model had insufficient examples
to learn meaningful per-class visual structure. Every category in the Quick Draw
dataset has 100,000+ images available, so increasing to 1,000 per class was
straightforward. Training time increased ~3.45x per epoch.


Embedding Dim Reduction
-----------------------
Reduced emb_dim from 256 to 128.
Rationale: the task is binary image generation over a fixed 345-class vocabulary.
128 dims (16 per head with 8 heads) is sufficient capacity for this task, and
reduces model size and training time. Aligns with the project's intentional
minimalism for Redstone reimplementation.


Why Output Quality is Limited
------------------------------
1. No spatial inductive bias — the model generates pixels left-to-right,
   top-to-bottom as a flat sequence. Transformers must learn spatial locality
   from scratch, unlike CNNs or diffusion models.

2. Class imbalance — Quick Draw images are ~90% white background. The model
   is heavily biased toward predicting white pixels, since doing so minimises
   loss cheaply.

3. Effectively a lookup table — with one word token per image and 345 fixed
   classes, the model learns one representative pixel distribution per class
   rather than composable visual concepts. This is acceptable given the goal
   is Redstone reimplementation.

4. Loss plateau — training loss converged to ~0.097 by epoch 3, with train
   and val loss nearly identical (no overfitting). More epochs yield diminishing
   returns without architectural changes.


Class Weighting
---------------
Problem: cross-entropy loss is dominated by correctly predicting white pixels
(~90% of all pixels). The model rarely commits to drawing black pixels.

Fix: added per-class weights to the cross-entropy loss.
  - All-white patch / white pixel token: weight 1.0
  - Black pixel / ink-containing patch tokens: weight 9.0

The 9.0 weight reflects the approximate 9:1 ratio of white to black pixels
in Quick Draw images. This forces the model to pay more attention to the rare
black pixels that actually define the drawing.


Patch Tokenization
------------------
Problem: pixel-level tokenization produces sequences of 784 tokens. This makes
training slow and makes it hard for the transformer to attend across the image.

Solution: 2x2 patch tokenization.
  - Each 2x2 block of pixels (4 binary values) is treated as one token.
  - 2^4 = 16 possible patch values (0 = all white, 15 = all black).
  - 28x28 image → 14x14 = 196 patches.
  - Context length: 785 → 197 (4x reduction).
  - Vocab size: 347 → 361 (345 words + 16 patch values).

Encoding: reshape 28x28 grid into 14x14 blocks of 2x2, read each block as a
4-bit binary number (row-major), offset by pixel_start_id (345).
Decoding: reverse the bit-unpacking and reshape back to 28x28.

Tradeoff: the model reasons at patch granularity rather than pixel granularity,
but the shorter sequence means attention can span the full image more easily.

Why not larger patches?
  Patch values grow as 2^(patch_size^2):
    1x1 →       2 values (current pixel tokens)
    2x2 →      16 values  ← chosen
    4x4 →  65,536 values  (borderline feasible)
   28x28 → 2^784 values   (impossible)

Class weighting with patches: all 15 non-zero patch values (those containing
at least one black pixel) are weighted 9.0.


Temperature Experimentation
----------------------------
The generation function uses top-k sampling with temperature scaling.
Temperature controls how "sharp" or "random" the output distribution is:
  - Low temperature (e.g. 0.5): model picks the most likely patches → more
    structured but potentially repetitive
  - High temperature (e.g. 1.5): more random sampling → more variety but
    potentially noisy

Visualisation updated to show a side-by-side grid of generated images across
multiple temperatures per word, saved to the generated/ folder.

Temperatures tested: 0.5, 0.8, 1.0, 1.2, 1.5


Top-k Experimentation
----------------------
With pixel-level tokenization, top-k was hardcoded to 2 (only black or white).
With 16 patch values available after patch tokenization, top-k can be varied:

  k=2:  only the two most likely patch types sampled
  k=4:  top 4 patch types
  k=8:  top 8 patch types
  k=16: unconstrained across all patch types

Visualisation extended to a 2D grid: temperatures across columns, top-k values
down rows. This allows direct visual comparison of all (k, temperature) combos.

Top-k values tested: 2, 4, 8, 16

Next Steps / Open Questions
